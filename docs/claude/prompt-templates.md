# 派工 Prompt 模板

複製、填空、派出。`{...}` 是填空處。每份模板已內建三件套（目標動機/驗收條件/回報格式）與回報合約，不要刪掉這些段落。model 建議見 `delegation.md` §3，升降級見 §5。

## 1. 搜尋 / 定位（subagent_type: Explore，model: sonnet；單純關鍵字定位可 haiku）

```
目標：找出 {要找的東西，例如「所有呼叫 addAutoMovementToDailyLog 的位置」}。
動機：{為什麼要找，例如「要改它的參數簽名，需要知道波及範圍」}。
範圍：{目錄/檔案範圍，例如 src/ 全部；不確定就寫「整個 repo，排除 dist/ 與 node_modules/」}。
驗收條件：
- [ ] 範圍內窮舉（說明你用了哪些搜尋 pattern，包含別名/re-export 的可能）
- [ ] 每個結果附 檔案:行號
回報格式：每個結果一行「檔案:行號 — 一句話說明脈絡」；最後給總數。
不要貼程式碼段。找不到就回「找不到」+ 用過的 pattern 清單，嚴禁編造。
```

## 2. 實作（subagent_type: claude 或 general-purpose，model: sonnet）

```
目標：{做什麼，例如「在 src/routes/system.js 新增 GET /api/system/xxx」}。
動機：{使用者原始需求的一句話版本，讓你在邊界情況能自行取捨}。
已知脈絡：{主對話已查明的事實：相關 檔案:行號、要複用的 helper、要遵守的慣例}。
必守規則：先讀 CLAUDE.md 的「不變式」與「⚠️ 陷阱」兩節；動到 {排程同步/KiDit/模式} 就先讀 docs/claude/architecture.md 對應節。
驗收條件：
- [ ] {具體行為條件，例如「GET /api/system/xxx 回傳 {...} 格式，未帶 token 回 401」}
- [ ] 改過的每個檔通過 node --check
- [ ] npm run smoke:tph-angular 全數 PASS
- [ ] 不引入 CLAUDE.md 不變式違規（DB 單例、參數化 SQL、camelCase 回應）
回報格式：改了哪些檔（檔案:行號範圍 + 每檔一句話）、驗證指令與結果各一行、未盡事項或風險（沒有寫「無」）。上限 30 行，不貼整段程式碼。
卡住兩次就停：回報失敗軌跡（試過什麼/確切錯誤/假設），不要硬做。
```

## 3. 重構 / 批次套用（模式已定案時 model: haiku 或 sonnet）

```
目標：把以下「已驗證的修改模式」套用到列出的每個位置。
模式（照抄，不要自由發揮）：
{貼上修改前→修改後的具體範例一則}
套用位置：{檔案:行號 清單——由主對話或搜尋 agent 先產出，不要讓套用者自己找}
驗收條件：
- [ ] 清單上每個位置都處理（處理不了的標出來，不要跳過不報）
- [ ] 除了模式規定的改動，不動任何其他程式碼（不順手重構、不改格式）
- [ ] 每個改過的檔通過 node --check
回報格式：「N/M 個位置完成」+ 例外清單（位置 + 為何不能套）+ node --check 結果一行。
遇到與模式範例不吻合的位置：不要自行變形，列入例外回報。
```

## 4. 研究（subagent_type: general-purpose，model: sonnet；結論影響架構決策時 opus）

```
問題：{要回答的問題，例如「better-sqlite3 v12 在 Windows + PM2 下的已知問題」}。
動機：{這個答案會決定什麼，例如「決定要不要升級依賴」}。
來源優先序：官方文件/官方 repo issue > 高信度技術文章 > 論壇。每個關鍵結論都要附來源 URL。
驗收條件：
- [ ] 直接回答問題（先給一句話結論，再給依據）
- [ ] 區分「查證過的事實」與「推測」，推測要標明
- [ ] 與本專案相關性：對照我們的版本/環境（{版本資訊}）說明適不適用
回報格式：結論（≤3 行）→ 依據條列（每條附來源）→ 對本專案的建議（≤3 行）。
超過 40 行就寫成檔案放 {路徑}，回覆只給路徑+摘要。查不到就說查不到。
```

## 5. 審查（subagent_type: claude，model: sonnet；高風險 diff 用 opus 或雙 agent 交叉）

```
目標：審查 {分支/diff 範圍，例如「git diff onsite-main..HEAD」}，找出會出錯的地方。
動機：{這個 diff 要做什麼}。你的立場是對抗性的：假設裡面有 bug，去證明它。
必查清單：
- [ ] .claude/skills/code-review.md 的專案 checklist 逐節過一遍
- [ ] CLAUDE.md「⚠️ 陷阱」七條是否被違反
- [ ] 每個宣稱的行為改動，指出對應的驗證證據在哪（沒有就列為 finding）
- [ ] 邊界：空值/JSON.parse 失敗/日期跨日跨時區/RBAC 缺漏
回報格式：finding 按嚴重度排序，每條 =「檔案:行號 — 一句話缺陷 — 具體失敗情境（什麼輸入→什麼錯誤結果）」。
確定的 bug 與「可疑但未證實」分開列。沒有 finding 就明說沒有，不要硬湊。上限 30 行。
不要修，只審。
```

## 驗收派工（固定用 `.claude/agents/verifier.md`）

```
Agent(subagent_type: "verifier", prompt: "
宣稱：{某工作已完成的一句話}。
驗收條件：{從原始需求抄來的可勾選清單——注意：對照需求，不是對照實作者說做了什麼}
背景：改動範圍大致在 {檔案清單}。")
```
