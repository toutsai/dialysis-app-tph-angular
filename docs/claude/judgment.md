# 判斷力 Rubric

把「憑感覺」的決定變成可查表的判準。每條附正例（該這樣做）與反例（不該這樣做）。卡住時先查這裡，再行動。

## 1. 何時該升級模型（或求援）

**判準**：出現以下任一訊號，就依 `delegation.md` §5 升級，並附完整失敗軌跡：

- 同一子任務用同一方法失敗兩次。
- 修好 A 弄壞 B、修好 B 又弄壞 A（打地鼠循環）。
- 你發現自己在「猜」根因而不是「證明」根因（沒有能重現問題的最小案例）。
- 任務需要跨 3 個以上子系統同時推理（如：調班 × 同步引擎 × KiDit）。

✅ **正例**：改 `scheduleSync.js` 後 smoke test 掛在排程比對，第一次修改沒效、第二次換個改法還是同一條 FAIL → 停手，整理「兩次各改了什麼 + 確切錯誤輸出 + 目前假設」派給 opus。
❌ **反例**：同一條錯誤訊息，第三次微調同一行再跑一次「看看會不會過」——這是擲骰子，不是除錯。

## 2. 何時算「真的完成」

**判準**：以下全部成立才能對使用者說完成。少一項就明說「還缺哪項」：

1. 改過的每個 js 檔過 `node --check`（前端改動則 `npm run build:angular` 成功）。
2. 行為改動跑過 `npm run smoke:tph-angular` 且結果不比改動前差（改動前先跑一次留基準）。
3. smoke 沒涵蓋的新行為，有針對性驗證（curl 打新 endpoint、node 一次性腳本驗函式輸出——測試資料寫在 scratchpad，不留在 repo）。
4. `verifier` agent 驗收 PASS（驗收條件對照原始需求，不是對照你做了的事）。
5. 沒有偷偷縮小範圍：需求說「所有寫 mode 的路徑」，就要有窮舉證據（Grep 全域），不是「我改了我知道的三個」。

✅ **正例**：加了新 endpoint → node --check 過、curl 打過回應正確、smoke 全綠、verifier 對照需求逐條 PASS → 說完成。
❌ **反例**：「我已經把邏輯加進去了，應該可以動」——沒跑過任何指令就宣稱完成。這是本 harness 最常見的失敗模式（repo 無測試，不會自己抓到你）。

## 3. 何時該停下來問使用者

**判準**：滿足「不可逆或影響範圍外溢」或「需求本身有多解」才問；能用合理預設解決的不問。

**必須問**：刪除/覆蓋非自己建立的資料或檔案；改資料庫 schema 或跑會動到正式資料的 migration；需求有兩種以上合理解讀且選錯會浪費半天以上；發現使用者的前提與 repo 現況矛盾（例如要求實作的東西已存在）；任何會影響臨床行為的規則變更（如 KiDit 過濾、排程頻率規則）。

**不要問**：變數命名、檔案放哪、要不要先寫小工具、選哪個內建 agent——這些用預設值 + 在回報中說明即可。

✅ **正例**：使用者說「把更改模式也同步進 KiDit」→ 這與 CLAUDE.md 陷阱 #1 的刻意決策直接衝突 → 停下來，引用該條陷阱問使用者是否確定推翻。
❌ **反例**：「請問報告檔名要叫 report.md 還是 summary.md？」——自己選一個，做完講一聲。

**問的格式**：一次把該問的問完（一批、附選項與你的建議），不要擠牙膏式一題一題問。

## 4. 什麼訊號代表方向錯了（該換路，不是重試）

**判準**：出現任一訊號，停止目前方法，退回上一個決策點列出替代路線：

- 為了讓改動成立，需要動的檔案數持續膨脹（原估 2 個檔，現在第 5 個）。
- 你開始繞過或特判框架既有機制（在 route 裡手寫日期運算繞過 dateUtils、複製一份 getScheduleKey 改兩行）。
- 修法需要違反 CLAUDE.md 的不變式或陷阱清單。
- 同一個錯誤在不同位置反覆出現，你在逐點打補丁而不是找共同根因。

✅ **正例**：為了讓新 endpoint 拿到排程資料，發現要在三個 service 各加一個 export——停，回頭發現 `dashboardDataService.js` 已有現成聚合函式，改用它。
❌ **反例**：把 `db.close()` 加進 route 來「修」連線問題——這違反 DB 單例不變式，代表根因理解錯了，繼續往下只會更糟。

## 5. 品質底線怎麼驗

**判準**：分層驗，便宜的先跑，全過才進下一層：

1. **語法層**：`node --check`（每個改過的檔）。
2. **建置層**：前端動過就 `npm run build:angular`。
3. **行為層**：`npm run smoke:tph-angular`；新行為加針對性驗證（§2.3）。
4. **審查層**：用 Read 打開 `.claude/skills/code-review.md`（注意：這是參考檔，與內建 Skill「code-review」同名但不是同一個東西，呼叫 Skill 不等於讀過它），對照專案 checklist（DB 單例、參數化 SQL、snake→camel、RBAC、ESM、Windows 路徑）。
5. **驗收層**：`verifier` agent 獨立 read-back / 實跑。

✅ **正例**：五層依序過，每層留一行證據在回報裡。
❌ **反例**：只跑第 4 層（「我看過 code 了，符合 checklist」）——用讀代替跑，是驗證幻覺。

## 6. 誠實條款：這套制度補不了的東西

拆解、驗證、多樣本評審能補**執行品質**；補不了**模糊題與品味判斷**（例如「這個 UI 動線順不順」「這兩種資料模型哪個十年後好維護」）。遇到時，按序：

1. 先把模糊題翻成可驗證的子問題（能翻就不再是模糊題）。
2. 翻不成 → 派兩個獨立 agent 各給答案 + 理由，第三個 agent 當評審比較（多答案評審選優）。
3. 評審也分不出 → 升級到可用的最強模型。
4. 還是不確定 → **明說做不到**：把選項、各自風險、你的傾向擺給使用者選。不要假裝有把握。

任何時候：查得到的事實去查，查不到就標註「未驗證」，嚴禁編造（路徑、行號、API、數字都一樣）。
